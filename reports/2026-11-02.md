### FastAPI

#### [URGENT BUGFIX | silent wrong values or 422] Omitted bool form fields changed twice

- **What changed:** In 0.147.0 (19 Oct), omitted `bool` form fields were read as `False`, including required fields and fields whose default is `True` or `None`. In 0.162.0 (23 Oct), this was reverted: omitted fields now use their declared default or raise a missing-field error.
- **Potential impact:** Confirmed by release notes. For unchecked HTML checkboxes on 0.147.0–0.161.x, a field with default `True` could silently become `False`. On 0.162.0, required bool fields that used to receive `False` may now return 422.
- **Exposure:** Unknown. Affected range per release notes: 0.147.0 through 0.161.x. Check any Form models with `bool` fields.
- **How to benefit:** Add tests that submit forms with checkboxes unchecked and with fields omitted. Assert the expected value and status code. Then pin `fastapi>=0.162.0` if the tests pass.
- **Source:** [FastAPI releases](https://github.com/fastapi/fastapi/releases)

#### [HIGH BUGFIX | request failures] Explicit JSON `null` is no longer treated as omitted

- **What changed:** In 0.151.0 (20 Oct), JSON `null` is distinguished from an omitted value. A `null` sent for a non-nullable body parameter is rejected, even if the parameter has a default.
- **Potential impact:** Confirmed by release notes. Clients that send `null` for optional body fields may now get 422 responses.
- **Exposure:** Unknown. Affected from 0.151.0 onward. Related 0.149.0, 0.150.0, and 0.153.0 changes also treat empty form strings and unselected file inputs as missing.
- **How to benefit:** Send `null` and omitted values to each body endpoint in a regression test. Make fields `Optional[...]` where `null` is valid.
- **Source:** [FastAPI releases](https://github.com/fastapi/fastapi/releases)

#### [HIGH BUGFIX | silent validation change] Defaults for omitted inputs are no longer validated

- **What changed:** In 0.148.0 (19 Oct), defaults for omitted Query, Header, Cookie, and Form parameters and model fields are not validated unless `validate_default=True` is set.
- **Potential impact:** Confirmed by release notes. Validators that used to run on defaults may now be skipped, so invalid default values can pass silently.
- **Exposure:** Unknown. Affected from 0.148.0 onward.
- **How to benefit:** Find validators that rely on default values. Add `validate_default=True` where needed. Add a test for each default value.
- **Source:** [FastAPI releases](https://github.com/fastapi/fastapi/releases)

### Pydantic

#### [HIGH BUGFIX | security and JSON contract] GHSA-qpmf-fgh3-ff25 and JSON extra-key handling in 2.14.2

- **What changed:** Released 29 Oct 2026. The release fixes GHSA-qpmf-fgh3-ff25 (Moderate, CVSS v4 6.3, no CVE assigned). Per the advisory, JSON validation with `extra='allow'` did not validate types of extra keys. Affected range: `>=2.13.0,<2.14.2`. Patched in 2.14.2. Python-mode validation is not affected. The release also fixes GHSA-3r8g-cqwr-jr29 (extra data matching a field name is ignored in TypedDict and dataclasses with `extra=allow`).
- **Potential impact:** Confirmed by release notes and advisory. JSON keys that match unused alias or field names are now treated as extra data. With `extra='forbid'`, these keys now raise a ValidationError where they were previously dropped. This can affect API request contracts.
- **Exposure:** Unknown. Check the installed Pydantic version and any `extra=` settings.
- **How to benefit:** Upgrade to 2.14.2 after running JSON request tests on models with `extra='forbid'` and alias generators.
- **Source:** [Pydantic releases](https://github.com/pydantic/pydantic/releases/tag/v2.14.2); [GHSA-qpmf-fgh3-ff25](https://github.com/pydantic/pydantic/security/advisories/GHSA-qpmf-fgh3-ff25); [GHSA-3r8g-cqwr-jr29](https://github.com/pydantic/pydantic/security/advisories/GHSA-3r8g-cqwr-jr29)

#### [HIGH BUGFIX | validation outcomes] Decimal and timedelta validation tightened in 2.14.1

- **What changed:** Released 11 Oct 2026. The Python `Decimal` validator now enforces the `max_digits` whole-digits limit (#13972). Out-of-range int inputs for `timedelta` are rejected (#13973).
- **Potential impact:** Confirmed by release notes. Values that were accepted before may now fail validation. Behaviour in 2.14.0 for these inputs is not stated in the notes [INCOMPLETE EVIDENCE].
- **Exposure:** Unknown. Relevant to models with `Decimal(max_digits=...)` or `timedelta` fields.
- **How to benefit:** Test boundary values for Decimal and timedelta fields before upgrading. Compare the results on 2.14.0 and 2.14.1.
- **Source:** [Pydantic v2.14.1 release](https://github.com/pydantic/pydantic/releases/tag/v2.14.1)

#### [HIGH BUGFIX | security, V1 only] Three security fixes in 1.10.27, the last V1 release

- **What changed:** Released 29 Oct 2026. This is the last V1 release. V1 support, including the `pydantic.v1` namespace in Pydantic 2, ends after this release. It fixes GHSA-49g6-96jj-f7r9 (`unique_items` check now runs in linear time for builtin scalars), GHSA-r49w-vh47-r4hf (internal `__pydantic` attributes ignored when setting dataclass extra values), and GHSA-jfv7-ghgv-gx4x (ISO 8601 durations accept only `.` as the decimal separator).
- **Potential impact:** Confirmed by release notes. Plausible risk: slow uniqueness checks on large inputs (denial of service) in V1 code. Applies only if V1 is in use.
- **Exposure:** Unknown. Check for `pydantic<2` pins and `pydantic.v1` imports.
- **How to benefit:** If V1 is in use, schedule migration to Pydantic 2. Until then, use 1.10.27 and monitor its security advisories.
- **Source:** [Pydantic v1.10.27 release](https://github.com/pydantic/pydantic/releases/tag/v1.10.27)

### SQLAlchemy

#### [URGENT BUGFIX | silent wrong query results] Expanding IN parameter names can collide

- **What changed:** Released 21 Oct 2026 in 2.1.6. An expanding IN parameter name can collide with another bound parameter, which silently replaces its value (#13695). The fix is backported to 2.0.56, which is not released yet.
- **Potential impact:** Confirmed by changelog. Plausible risk: a query returns results for the wrong values without an error. The changelog does not state the affected version range [INCOMPLETE EVIDENCE].
- **Exposure:** Unknown. Relevant to queries that combine `in_()` with other bound parameters.
- **How to benefit:** Upgrade 2.1.x to 2.1.6. For 2.0.x, no released fix exists yet, so check for affected queries and watch for 2.0.56. Add tests that combine IN lists with other filters and compare results.
- **Source:** [SQLAlchemy 2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html); [ticket #13695](https://www.sqlalchemy.org/trac/ticket/13695); [PyPI SQLAlchemy](https://pypi.org/project/SQLAlchemy/)

#### [URGENT BUGFIX | silent wrong results] selectinload on many-to-many ignores extra join criteria

- **What changed:** Released 2 Oct 2026 in 2.1.2. selectinload on a many-to-many relationship ignores extra `primaryjoin` criteria and loads rows that should be excluded (#13626). The changelog says this is a regression from #5987 but does not state the affected version range [INCOMPLETE EVIDENCE].
- **Potential impact:** Confirmed by changelog. Plausible risk: relationship collections contain extra rows without any error.
- **Exposure:** Unknown. Relevant only to many-to-many relationships with extra `primaryjoin` criteria.
- **How to benefit:** Upgrade to 2.1.2 or later. Add a test that checks the exact contents of a filtered many-to-many relationship loaded with selectinload.
- **Source:** [SQLAlchemy 2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html); [ticket #13626](https://www.sqlalchemy.org/trac/ticket/13626)

#### [HIGH BUGFIX | stale ORM values] Bulk `update()` left stale values on most matched objects

- **What changed:** Released 16 Oct 2026 in 2.1.5 and 2.0.55. An ORM `update()` whose WHERE clause matches several session objects left server-side and SQL-expression values stale on all but one object (#13675). The changelog says this is a regression from #11917 introduced in 2.0.36.
- **Potential impact:** Confirmed by changelog. Plausible risk: in-session objects show old values, and a later flush could write them back.
- **Exposure:** Unknown. Affected range per changelog: from 2.0.36 until the fix in 2.0.55 and 2.1.5 [INCOMPLETE EVIDENCE on the exact 2.1.x range].
- **How to benefit:** Upgrade to 2.0.55 or 2.1.5. Add a test that runs a multi-row ORM update and then checks each loaded object.
- **Source:** [SQLAlchemy 2.1 changelog](https://docs.sqlalchemy.org/en/21/changelog/changelog_21.html); [ticket #13675](https://www.sqlalchemy.org/trac/ticket/13675); [SQLAlchemy releases](https://github.com/sqlalchemy/sqlalchemy/releases)
