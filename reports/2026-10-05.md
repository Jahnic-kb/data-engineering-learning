#### `fastapi`

**[HIGH BUGFIX | API startup failures] 0.142.2 allows startup when automatic OpenTelemetry configuration fails**

- **What changed:** FastAPI 0.142.2, released September 30, 2026, allows application startup to proceed when automatic OpenTelemetry configuration fails. [Official release note](https://github.com/fastapi/fastapi/releases/tag/0.142.2)
- **Potential impact:** The upstream failure mode is confirmed. It could affect Kienbaum APIs that use automatic OpenTelemetry configuration if that setup errors; no Kienbaum incident is known.
- **Exposure:** Setups using automatic OpenTelemetry configuration are relevant; the release note does not specify a finer affected-version range. Fixed in 0.142.2. Kienbaum exposure: **unknown**.
- **How to benefit:** Check the FastAPI pin and test startup both with a valid telemetry configuration and with an unavailable or invalid exporter. Upgrade to 0.142.2 or later if the test applies.

#### `SQLAlchemy`

**[HIGH BUGFIX | incorrect ORM rows] 2.1.2 fixes filtered many-to-many `selectinload()` results**

- **What changed:** SQLAlchemy 2.1.2, released October 2, 2026, fixes a regression where many-to-many `selectinload()` could ignore additional `relationship.primaryjoin` criteria and load related rows that should have been excluded. [Official 2.1 changelog](https://www.sqlalchemy.org/docs/latest/changelog/changelog_21.html#change-2.1.2-orm)
- **Potential impact:** The incorrect filtering behavior is confirmed upstream. It could produce over-inclusive ORM results in applications using that relationship-loading pattern; no Kienbaum impact is confirmed.
- **Exposure:** The changelog identifies a regression but does not state the first affected version; it is fixed in 2.1.2 and remains fixed in the documented 2.1.3 release. Kienbaum exposure: **unknown**. [SQLAlchemy 2.1 changelog](https://www.sqlalchemy.org/docs/latest/changelog/changelog_21.html)
- **How to benefit:** If using SQLAlchemy 2.1, test many-to-many relationships with extra join criteria and upgrade to the current 2.1 patch. Compare returned IDs against expected filtered results.

#### `future`

**[HIGH BUGFIX | parallel worker crashes] 1.76.0 fixes backend crashes and working-directory failures**

- **What changed:** `future` 1.76.0 fixes failures when the current working directory cannot be entered—a regression introduced in 1.40.0—and crashes when deprecated `gc = TRUE` is used with `multisession` or `cluster` backends. CRAN lists 1.76.0 as published September 24, 2026. [Official NEWS](https://cran.r-project.org/web/packages/future/news/news.html) · [CRAN package index](https://cran.r-project.org/web/packages/future/index.html)
- **Potential impact:** The crash and worker-failure cases are confirmed upstream. They could break parallel workloads under these specific conditions; no Kienbaum impact is known.
- **Exposure:** `gc = TRUE` on `multisession` or `cluster` is affected before 1.76.0; the working-directory regression was introduced in 1.40.0 and fixed in 1.76.0. Kienbaum exposure: **unknown**.
- **How to benefit:** Check future calls for `gc = TRUE`, test worker startup and task execution, then upgrade to 1.76.0 or later if applicable.

#### `openxlsx`

**[HIGH FEATURE | stale report values] 4.2.9 adds clean worksheet rewrites**

- **What changed:** `openxlsx` 4.2.9, published September 2, 2026, fixes date detection and adds opt-in `overwrite` support to `writeData()`. With `overwrite = TRUE`, existing worksheet cell data is cleared before writing, so a shorter replacement dataset does not leave stale trailing rows. [Official NEWS](https://cran.r-project.org/web/packages/openxlsx/news/news.html) · [CRAN package index](https://cran.r-project.org/web/packages/openxlsx/index.html) · [Implementation and example](https://github.com/ycphs/openxlsx/pull/536)
- **Potential impact:** Stale rows in a shrinking report are a documented upstream scenario. In recurring Kienbaum reports, they could make exported data incorrect or retain values that no longer belong in the report; there is no evidence this has occurred.
- **Exposure:** Builds before 4.2.9 do not have this flag; in 4.2.9 it is opt-in and defaults to `FALSE`. Kienbaum exposure: **unknown**.
- **How to benefit:** Pilot `writeData(..., overwrite = TRUE)` only for intended full-sheet data rewrites. Check that styles, formulas, and other workbook content remain correct. The package NEWS says `openxlsx` is maintained but no longer in active development, so test this workflow before production use.

#### `pandas`

**[HIGH BUGFIX | silent wrong results] 3.0.6 fixes CSV, Arrow, and index regressions**

- **What changed:** pandas 3.0.6, released September 17, 2026, fixes several regressions: `read_csv(sep=None)` could fail to infer separators and, with unsupported engines, silently treat each line as one column; PyArrow-backed linear interpolation could leave missing values or truncate integer results; and external mutation could silently corrupt a `RangeIndex` because of missing Copy-on-Write tracking. It also fixes a PyArrow-backed assignment that could share memory unexpectedly. [Official pandas 3.0.6 release notes](https://pandas.pydata.org/docs/whatsnew/v3.0.6.html)
- **Potential impact:** These upstream behaviors include incorrect parsing and silent result corruption. They could affect Kienbaum data preparation or analysis when using the named code paths; no Kienbaum impact is known.
- **Exposure:** The changelog groups regression fixes but does not state an affected-version range for each issue. All are fixed in 3.0.6. Kienbaum exposure: **unknown**.
- **How to benefit:** Check pandas pins and test separator inference, PyArrow interpolation and assignment, and index immutability. Upgrade to 3.0.6 or later after those checks.

**[HIGH BUGFIX | process crashes] 3.0.5 fixes a Python 3.14 segmentation fault**

- **What changed:** pandas 3.0.5, released July 22, 2026, fixes a segmentation fault in pandas 3.0.4 wheels on Python 3.14 caused by building against an incompatible NumPy version. [Official pandas 3.0.5 release notes](https://pandas.pydata.org/docs/whatsnew/v3.0.5.html)
- **Potential impact:** The process-crash condition is confirmed upstream. It could interrupt jobs using the affected wheel/runtime combination; no Kienbaum impact is known.
- **Exposure:** pandas 3.0.4 wheels on Python 3.14 are affected; fixed in 3.0.5. Kienbaum exposure: **unknown**.
- **How to benefit:** Check deployed Python and pandas versions together. If using this combination, upgrade to 3.0.5 or later and run representative data pipelines before redeployment.

#### `asyncmy`

**[URGENT BUGFIX | SQL injection risk] 0.2.12 removes unsafe `escape_dict`**

- **What changed:** asyncmy 0.2.12, released August 6, 2026, removes `escape_dict`; the release notes state that dictionary keys could reach SQL unescaped. The GitHub-reviewed advisory for CVE-2025-65896 describes SQL injection through crafted dictionary keys and rates it Critical, CVSS 9.8. [asyncmy 0.2.12 release notes](https://github.com/long2ice/asyncmy/releases) · [GitHub Advisory Database: CVE-2025-65896](https://github.com/advisories/GHSA-qhqw-rrw9-25rm)
- **Potential impact:** The advisory confirms a SQL-injection risk if attacker-controlled keys reach the vulnerable helper. Whether Kienbaum code has this path is unknown.
- **Exposure:** The advisory lists affected versions as `<= 0.2.11` and **Patched versions: None**. Although 0.2.12 removes the helper, do not treat it as formally patched solely on that basis. Kienbaum exposure: **unknown**.
- **How to benefit:** Immediately inventory asyncmy versions and search application code for `escape_dict`. Remove that call path, use parameterized SQL, and confirm remediation with the maintainer or a verified advisory update before declaring the vulnerability patched.

**[URGENT BUGFIX | database traffic confidentiality] 0.2.14 makes `ssl=True` negotiate TLS**

- **What changed:** asyncmy 0.2.14, released August 12, 2026, fixes `ssl=True` silently connecting in plaintext by building a default TLS context; invalid SSL arguments now raise `ValueError` rather than disabling TLS. [Official asyncmy releases](https://github.com/long2ice/asyncmy/releases)
- **Potential impact:** The plaintext behavior is confirmed upstream. It could expose database traffic if a deployment used `ssl=True` with an affected version; no Kienbaum exposure is known.
- **Exposure:** Affected versions are those before 0.2.14 when using the relevant SSL options; fixed in 0.2.14. Kienbaum exposure: **unknown**.
- **How to benefit:** Inventory asyncmy pins and TLS configuration, upgrade where relevant, and verify encrypted handshakes in an integration test. Confirm that invalid SSL configuration fails closed.

**[HIGH BUGFIX | pool hangs and dropped read events] 0.2.15 hardens reads and shutdown**

- **What changed:** asyncmy 0.2.15, released September 21, 2026, fixes `read_timeout` losing data, EOF, or error notifications under a timing race; multiple `Pool.wait_closed()` hang and cancellation/shutdown cases; and pool waiters not being notified when a connection attempt fails. It also makes writes to closed transports raise DBAPI `OperationalError`, allowing SQLAlchemy `pool_pre_ping` to recognize and replace a disconnected connection. [Official asyncmy 0.2.15 release notes](https://github.com/long2ice/asyncmy/releases/tag/v0.2.15)
- **Potential impact:** The read-loss and pool-hang conditions are confirmed upstream. They could cause failed requests or stalled shutdown under the affected timing and pool conditions; no Kienbaum impact is known.
- **Exposure:** Before 0.2.15 for the described cases; the `read_timeout` race is noted especially on Python 3.9/3.10. Kienbaum exposure: **unknown**.
- **How to benefit:** Upgrade to 0.2.15 or later after testing read timeouts, cancelled pool shutdown, failed connection creation, and `pool_pre_ping` recovery.
